Главная находка: повтор передачи клиента Открыто у нас

У Amazon правило: любую операцию с последствиями должно быть безопасно повторить. Каждый запрос несёт свой уникальный ID; повтор с тем же ID возвращает прежний результат, а не делает работу второй раз. В нашем плане так защищены только начисления (уникальный ID оплаты). Передача клиента не защищена.

Сценарий 1 — двойная отправкаПартнёр на плохой мобильной связи не дождался ответа и нажал «Отправить» ещё раз. Итог — две передачи и две сделки.
Сценарий 2 — повтор из очередиCRM создала сделку, но ответ потерялся. Агент досылает заявку из очереди — и создаёт дубль сделки.
Что предлагаюКабинет при открытии формы создаёт ID передачи. Сервер хранит его как уникальный и сохраняет вместе со сделкой. Перед повтором из очереди модуль проверяет, нет ли уже сделки с этим ID.

Источник: Amazon Builders' Library — «Making retries safe with idempotent APIs». Там же: повтор с тем же ID, но другими данными — это ошибка, а не новая операция; ID и сама операция записываются вместе, «всё или ничего». Отмечено на странице «Структура», сценарий 2.

П1Двери в одну сторонуAmazon

Джефф Безос (письмо акционерам, 2015): необратимые решения принимают медленно и вдумчиво, обратимые — быстро. Беда больших команд — тратить на обратимые столько же сил, сколько на необратимые.

У нас: в таблицу «что блокирует что» добавлена колонка «тип решения». На разговоре с заказчиком время — в первую очередь на необратимые и дорогие: Д3, Г1, Е2.

П7Условия готовности (Definition of Done)Microsoft

Готовый список на трёх уровнях. Задача: выполнены критерии приёмки, собирается без ошибок, юнит-тесты написаны и проходят, старые тесты проходят, достаточно журналирования, проверка кода, обновлена документация, владелец подтвердил. Итерация: плюс интеграционные, нагрузочные и сквозные тесты. Выпуск: готов к установке.

У нас: адаптировать, а не придумывать. «Владелец подтвердил» = пользователь смотрит результат.

П9Правила APIMicrosoft · Google

Единый формат ошибок, постраничная выдача длинных списков, ключ повтора для операций создания, 404 вместо 403 там, где нельзя выдавать сам факт существования.

П10Тесты по размерамGoogle

Маленькие — без внешних систем, миллисекунды; средние — с базой, на одной машине; большие — вся система. Примерно 70 / 20 / 10.

К запуску и обновлениям

М16–М17 и сопровождение
П12Чек-лист готовности к запускуAmazon · Google

Перед запуском — проверка по списку, составленному из прошлых сбоев: безопасность обновления, обнаружение проблем, кому звонить, план отката. У Google — чек-лист запуска в книге SRE (приложение E).

У нас: чек-лист установки у клиента: DNS, сертификат, почта с SPF/DKIM, cron, роли не пустые, юридические тексты, резервная копия, кто отвечает. Часть пунктов может проверять сама страница «Проверка».

ПредложениеAWS ORR →SRE →
П13Обновления в два шагаAmazon

Формат данных меняют в два выпуска: сначала версия умеет читать новое, но пишет по-старому; потом начинает писать новое. Старое удаляют, только когда все данные переписаны. Каждое обновление проверяют и откатом назад.

У нас: к «версии + миграции» модуля: новые поля и таблицы добавляем сразу, старые убираем только в следующей версии; обновление с прошлой версии проверяем на копии; резервная копия перед обновлением. Связано с открытым вопросом про updater.php.

Что у нас уже совпадает с практикой

  • Шаги разбора с вариантами и рекомендацией — у Microsoft это называется trade study: варианты, критерии, выбор, запись в журнал решений.
  • 404 вместо 403 для чужих данных — так же в гайдлайнах API Microsoft.
  • Уникальный ID оплаты против двойного начисления — тот же приём, что у Amazon.
  • Журнал начислений «только добавление», исправление — новой строкой: тот же принцип, что у журнала решений Microsoft.
  • DECISIONS.md в Markdown рядом с проектом — так советует Google Cloud для журнала решений.
  • Безопасность с первой стадии — основа Microsoft SDL.
